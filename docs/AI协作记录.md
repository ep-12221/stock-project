# AI 协作记录：关键 Prompt 与实现复盘

整理日期：2026-09-06。

本项目采用分阶段推进的 AI 协作方式：由我提出阶段目标、发起审查并决定后续推进方向，AI 根据项目文档细化方案、编写代码和执行回归验证。下面选取代码审查、问题修复、前端接入、故障恢复四个代表性案例，说明每次协作解决了什么问题，以及结果如何得到验证。

以下 Prompt 为根据项目上下文重构的整理版，将阶段目标、技术约束和验收要求集中表达，便于展示任务拆解与协作思路。实现结果与测试数据对应实际项目，测试数量为各阶段的验收快照。

## 1. 以需求文档为基准，检查已有实现

### 场景与目标

项目已经实现到 T04，具备内存账户、撮合核心和交易 API。继续扩展功能前，需要检查现有代码是否符合文档约定，尤其是身份状态、演示配置、错误处理和账户展示之间的一致性。

### 关键 Prompt（整理版）

> 目前股票模拟交易系统已经实现到 T04，包含内存账户、身份认证、限价撮合和交易 API。请先阅读题目、详细实现文档及阶段验收记录，再对照代码做一次审查。
>
> 审查重点：
> 1. 价格优先、时间优先、部分成交及资金 / 持仓冻结是否符合文档约定。
> 2. 登录、注册和账户读取在并发或请求失败时，能否保持 Cookie 与页面身份一致。
> 3. 环境配置、参数校验、异常状态码和账户展示是否存在边界问题。
> 4. 现有测试是否遗漏可能影响交易或身份状态的场景。
>
> 请先输出问题清单，按影响程度排序。每项包含触发条件、代码位置、实际影响和建议验证方式；区分已确认的问题与需要进一步验证的疑点。本轮先完成审查，修复范围根据审查结果确定。

### AI 输出与后续推进

AI 对照文档审查已有实现，归纳出四项需要修复的问题：

- 并发登录 / 注册的迟到响应可能导致 Cookie 与页面身份不一致。
- 关闭演示流动性的配置没有正确生效。
- 不支持的 JSON 字符集或内容编码被错误地返回为 500。
- 清仓后，首页仍将已归零的持仓计入持仓数量。

审查结果将后续工作收敛为四项具体修复，每项都有明确的触发条件和回归目标，下一轮协作围绕这份问题清单展开。

### 这次协作的价值

审查有了明确的参照：文档约定、现有代码和可观察的错误行为。每项发现都能落到修复位置和验收条件，为后续功能扩展建立可检查的基础。

详见 [T01～T04 审查修复验收](T01-T04审查修复验收.md)。其中的通过结果属于修复后的验收。

## 2. 将审查结论转化为回归测试和修复

### 场景与目标

上一轮已经明确四项问题，这一轮需要把发现落实为代码修复，并检查相邻的异常与并发场景。

### 关键 Prompt（整理版）

> 请根据上一轮审查的问题清单开始修复，保持现有接口和撮合规则的业务含义一致。
>
> 按“复现问题 → 补充回归测试 → 确认失败 → 修改实现 → 验证通过”的顺序推进。测试应检查用户可观察的行为或状态约束，避免只复述实现细节。
>
> 涉及异步请求和身份状态时，请检查相邻场景：响应顺序颠倒、部分请求失败、会话切换，以及操作锁是否过早释放。如果发现同一原因导致的其他问题，一并补充回归。
>
> 完成后运行完整检查，并用真实 HTTP 请求复验关键接口。按问题列出修复前后的行为、增加的测试和验证结果，同时说明仍然存在的限制。

### AI 输出与后续推进

这条指令承接上一步审查结果。AI 按项目约定先补充回归测试，确认测试能够复现问题，再实现身份操作互斥、演示开关严格解析、415 错误映射和非零持仓统计。

在继续检查认证边界时，AI 又发现：账户与行情读取并行执行，其中一个请求失败后，认证锁可能过早释放。该问题随后补充了独立回归并完成修复。

这一轮的调整集中在已有行为的正确性，没有引入新的撮合规则。具体测试设计和修复代码由 AI 完成；我在后续提出接入前端，继续推进交易闭环。

### 验证结果

首轮回归出现 27 项失败、69 项通过，修复后目标测试全部通过；后续认证边界回归同样经历了先失败、再通过的验证。最终新增 31 项测试，全量 **292 项测试**、类型检查、Lint、格式检查和生产构建通过，并完成真实 HTTP 与 Cookie 会话复验。

这次协作形成了可追溯的修复链条：问题描述、失败测试、实现修改、通过结果。详见 [T01～T04 审查修复验收](T01-T04审查修复验收.md)。

## 3. 将后端交易能力接入前端工作台

### 场景与目标

撮合引擎和交易接口已经具备，需要让用户能够通过页面完成查看行情、提交委托、查看持仓和核对成交的操作流程。

### 关键 Prompt（整理版）

> 后端撮合核心和交易 API 已完成，请按照 T05 计划，将真实接口接入 Vue 3 + TypeScript 前端，形成可操作的交易工作台。
>
> 页面需要覆盖账户概览、股票行情与选择、限价买卖、委托、持仓和成交历史。复用现有接口及共享类型，所有结算结果以服务端为准，价格使用整数分处理。
>
> 请重点设计异常流程：
> 1. 切换股票、筛选历史或刷新账户时，旧响应不能覆盖新状态。
> 2. 下单过程中防止重复提交；如果响应丢失、无法确认结果，需要保留原输入并明确提示待确认状态。
> 3. 登录失效和退出失败时，页面状态与操作权限要一致。
> 4. 提供加载、空数据和错误反馈，并保证手机宽度下能够完成主要操作。
>
> 按现有阶段边界实现，明确哪些更新暂时依靠刷新、哪些需要后续实时推送或幂等能力。完成组件与状态测试，再用两个隔离的浏览器账户验证买入、挂卖、部分成交和清仓流程。

### AI 输出与后续推进

AI 根据既有 T05 计划实现账户概览、股票选择、限价买卖表单、持仓列表和历史分页，并处理请求失败、身份失效及移动端布局。

实现过程中形成了三项关键处理：

- **结算以服务端为准。** 前端展示后端返回的账户与订单结果，金额使用整数分处理。
- **防止旧响应覆盖新状态。** 使用账户版本、行情版本和请求代次处理异步请求交错。
- **明确结果不明的订单状态。** 下单响应异常时保留输入并暂停新单，避免用户在不确定原单结果时直接再次提交。

AI 在复查中继续补充回归，修复退出失败时误清空历史、筛选列表可误开启未知订单确认等边界问题。后续阶段再补齐跨账户实时同步和服务端幂等，使功能按依赖顺序逐步闭合。

### 验证结果

T05 新增 79 项测试，全量 **371 项测试**及完整检查通过。真实 Chrome 中使用两个隔离账户完成买入、挂卖、部分成交和清仓，并验证请求失败、身份失效和手机布局。

T05 的账户更新仍包含手动刷新；后续 T06 完成实时推送和断线恢复，验收时全量测试达到 **482 项**。详见 [T05 前端工作台验收](前端工作台实现验收.md)与 [T06 实时链路验收](实时链路实现验收.md)。

## 4. 补齐响应丢失和页面刷新后的订单恢复

### 场景与目标

T06 已经完成实时行情、账户推送和断线恢复，下一阶段是 T07 下单幂等与稳定性。需要进一步处理一种关键情况：服务端已经接受订单，但浏览器没有收到响应，此时用户重试可能重复下单。

### 关键 Prompt（整理版）

> T06 已完成实时行情、账户推送和断线恢复。接下来实现 T07 下单幂等与故障恢复，重点解决“服务端已接受订单，但浏览器未收到响应”时的重复下单风险。
>
> 请先明确前后端协议，再实现以下行为：
> 1. 为每笔原始下单请求提供稳定标识，并按用户隔离；同标识、同参数重试应返回原订单，同标识、不同参数应返回冲突。
> 2. 重复确认不能再次冻结资产、创建订单或触发撮合。
> 3. 前端在发送前保存恢复所需的信息；页面刷新后仍能展示待确认委托，并按原标识和原参数由用户确认重试。
> 4. 处理会话切换与历史数据恢复，避免不同用户之间的待确认状态混用。
>
> 请通过回归测试和真实链路验证：成功订单的并发重放、响应丢失、浏览器等待响应时刷新，以及参数冲突。检查订单数量和资产变化，并说明单进程内存、浏览器存储及服务重启对恢复能力的限制。

### AI 输出与后续推进

AI 将故障恢复落实为前后端配合的方案：

- **后端识别同一笔请求。** 使用用户身份与 `clientOrderId` 保存成功订单映射；同标识、同参数重试返回原订单当前状态，同标识、不同参数返回冲突。
- **前端保存原始请求。** 发送前将请求写入当前标签页的 `sessionStorage`，结果不明或页面刷新后展示待确认委托。
- **由用户确认重试。** 按原标识和原参数重新确认订单，不自动生成新请求再次下单。

UUID、存储方式及响应规则由 AI 根据阶段目标细化实现。后续回归又覆盖了同用户会话替换、刷新锁释放以及历史窗口恢复等交错场景。

这一阶段把重复请求控制推进到了服务端，恢复范围也明确限定在当前进程的内存记录和同一个请求标识内。

### 验证结果

T07 新增 71 项测试，全量 **553 项测试**及完整检查通过，并补充真实链路验收：

- 创建成功订单后，使用同一标识并发重放 8 次，均返回同一张订单，没有再次冻结或撮合。
- 请求在真实后端成交后，截断返回浏览器的响应；确认重试返回原订单。
- 浏览器仍在等待下单响应时刷新页面，恢复待确认请求后再确认，最终没有重复成交。

详见 [T07 幂等与稳定性验收](幂等与稳定性实现验收.md)。

## 协作复盘

这组记录体现了三个实践要点：

1. **将上下文、目标、约束和输出要求写完整。** 明确已经完成什么、这一轮解决什么、需要遵守哪些规则以及如何验收，让任务范围和完成标准都有依据。
2. **将 AI 的修改落实为可验证结果。** 回归测试检查边界，真实 HTTP 检查接口与会话，浏览器流程检查用户操作，多种证据共同支撑阶段验收。
3. **把设计取舍与保证范围写清楚。** 前端防重复点击、服务端幂等、实时同步分别解决不同问题；内存存储、重启清空和原请求标识的限制也需要在交付中说明。

这些记录串联了从审查到修复、从功能接入到故障恢复的过程。面试讲解可以沿着具体案例展开：问题如何出现、实现如何处理、测试如何复现，以及当前方案适用于什么范围。
