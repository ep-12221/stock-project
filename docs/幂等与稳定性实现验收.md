结果：新增 71 项，当前 553 项全部通过（后端 312、前端 241），31 个测试文件；类型、ESLint、Prettier、生产构建全部通过。

## 1. 解决的问题与当前行为

HTTP 超时不代表服务端没有接受委托。原先页面只能暂停下单、让用户人工核对；如果用户再次提交一笔相同业务参数的请求，服务端无法判断它是重试还是新的交易。

T07 为每笔提交增加请求标识。原请求重试只会返回同一订单的当前状态；如果原请求从未受理，重试会提交这笔委托。前端在当前标签页中保存原参数，显示“重试并确认此委托”，不会因切换股票、行情变化或刷新页面而改用另一组参数。

新下单、原请求确认和已受理订单后的实时变化有各自清晰的行为：

- 正常首次提交：创建 UUID、保存原请求、POST，收到合法结果后解除待确认记录。
- 请求结果不明：暂停新下单，展示原股票、买卖方向、限价和数量。
- 原请求确认：用户显式点击重试，使用同一个 UUID 和原参数；不会受到首次成交后可用现金或可卖持仓减少的阻拦。
- 页面刷新：恢复登录与实时状态后，只恢复待确认卡片，不自动 POST。
- 订单继续成交：WebSocket 正常更新资产与历史；原请求重放会返回更新后的订单，不能重复冻结、扣款或撮合。

## 2. 公开接口契约

`POST /api/orders` 现在严格要求以下五个字段：

```json
{
  "symbol": "SIM001",
  "side": "BUY",
  "priceCents": 1001,
  "quantity": 100,
  "clientOrderId": "7d8dfe84-cc8d-4cc6-9f5f-55b6c6a57279"
}
```

clientOrderId 必须为 UUID，服务端规范化为小写；缺失、错误格式或额外字段返回 400。股票代码和买卖方向仍精确匹配既有规则，价格为整数分，数量为正整数股。userId 始终从已认证的服务端会话获取。

| 场景 | HTTP | 结果与副作用 |
| --- | --- | --- |
| 同用户的新标识，校验与结算成功 | 201 | 创建订单、冻结或撮合，并正常推送 |
| 同用户、同标识、同一组业务参数 | 200 | 返回原订单当前状态及当前本人快照，不再次提交 |
| 同用户、同标识、业务参数不同 | 409 / IDEMPOTENCY_CONFLICT | 不修改资产或原订单 |
| 不同用户使用同一标识 | 按各自首次请求处理 | 用户之间独立 |
| 校验、余额、持仓、上限、自成交或内部结算失败 | 对应错误 | 不创建成功标识映射，不留下部分结算 |

响应仍为 `{ data: { order, snapshot } }`。重放返回的是当前订单和当前账户快照，不缓存首次响应；原订单后来部分或全部成交，也能正确确认。公开订单 DTO 不新增用户或请求标识字段，匿名成交继续不含任何用户与订单身份。

这是接口变更：此前只发送四个业务字段的外部调用需要添加 clientOrderId。当前网页已自动生成，用户无需输入；scripts/verify-trading.mjs 也已适配。

## 3. 服务端实现与原子性

`MemoryStore.idempotentOrdersByUser` 保存用户 → 小写 UUID → `{ orderId, fingerprint }`。指纹是固定顺序的四个业务参数 symbol、side、priceCents、quantity，不包含会话或可变账户状态。

交易服务的公开入口 `submitOrder(userId, input)` 强制标识；可信内部入口 `submitLimitOrder` 允许系统种子与既有引擎测试省略标识，两者共用同步交易实现。输入中提供了标识时，即使走内部入口也必须合法。

执行顺序为：

1. 验证用户和输入结构，规范化 UUID，计算业务参数指纹。
2. 查询已成功的映射；命中则先比较指纹，再从订单存储中复制当前订单返回。
3. 未命中才检查股票、账户资产与活跃委托上限，预演撮合并创建独立结算草稿。
4. 所有数值、冻结和守恒校验通过后，同步提交账户、持仓、订单簿、成交、索引及成功映射，中间没有 await 或外部 I/O。
5. 路由对首次成功返回 201 并调用成交后推送；重放返回 200 并跳过推送回调。

幂等检查必须早于当前可用资金和订单上限，否则第一次已成功的请求可能因为它自己冻结了资金而在重试时被误拒绝。重放不增加账户版本、市场版本、订单序号或成交序号，也不改变挂单的时间优先顺序。

成功映射保留到该进程重启，失败不占用标识。新 store 没有旧映射；整个系统仍以单进程内存为唯一状态来源。

## 4. 客户端恢复与错误分类

`pending-order.ts` 在 sessionStorage 按 serverEpoch 和 userId 保存带版本的原请求记录。读取时校验身份、股票、方向、整数价格、数量和 UUID；写入后回读确认内容一致，之后才发送 POST。记录中没有 Cookie、密码或会话令牌。

trading store 保持单次操作门禁，同时检查登录身份、账户快照归属、实时同步状态及提交 / 刷新锁。`pendingOrder` 对外只读；`retryPending()` 读取原请求，不读取当前表单。每个网络回调还检查请求代次和登录会话代次，旧身份或旧请求不能解锁当前委托。

| 返回或故障 | 前端行为 |
| --- | --- |
| 合法成功响应，原业务参数一致 | 应用账户版本入口，清理恢复记录，允许新单 |
| 旧版本合法 HTTP 成功 | 不覆盖较新 WS 资产，但可以确认这笔原请求 |
| 网络失败、408、5xx、损坏或不匹配的成功响应 | 保留原请求，暂停新单，等待显式重试 |
| IDEMPOTENCY_CONFLICT | 显示参数冲突，保留原请求和新单锁，不自动更换标识 |
| 明确的其他业务拒绝 | 清理该尝试；普通 409 同步账户，保留具体失败原因 |
| 401 或确认的身份变化 | 清理可见私有状态并返回登录；不能跨身份重试 |
| 发送前存储不可读、不可写或写后回读不符 | 不发送 POST，提示恢复存储后再操作 |
| 收到结果后无法清理存储 | 保留原请求和新单锁，可在存储恢复后显式确认同一请求 |

实时推送、重连完成或手动刷新都不能替代对未知 HTTP 请求的确认。旧的人工“已核对”方法不能绕过 pending，页面已改为原请求重试按钮。

退出或切换用户只清除可见状态，不删除该用户的标签页恢复记录；同用户、同服务实例再次登录可以恢复。服务实例变化时不使用旧记录。sessionStorage 的恢复范围仅限相同来源、当前标签页生命周期，关闭标签页、清空存储、换浏览器或换设备不保证保留标识，应先核对订单历史。使用新 UUID 的相同参数请求仍表示新订单。

## 5. 本阶段发现并修复的交错问题

- 同一用户登录会话代次变化时，旧 refresh 的 finally 无权更新新身份，但也不能把 refreshing 永久留在 true。现在会话替换释放旧刷新锁，并屏蔽旧响应。
- 初始化恢复监听不能清掉已经缓存的完整账户历史窗口。首次进入只恢复 pending；实际身份变化才重置历史，防止旧 HTTP 页把已成交状态覆盖为活跃状态。
- 确认成功后存储清理失败，不能直接开放新单。原请求与新单锁继续保留，后续确认依旧使用原标识。

前两项都补充了先失败、后通过的回归；存储故障包含在首批先行测试中。

## 7. 真实 HTTP 与浏览器验收

### 并发重放

独立生产服务使用端口 4328、空订单簿。首次创建挂单后同时发送 8 个相同请求：全部返回 200、同一订单和同一账户快照，该用户最终仍只有 1 张订单、没有成交。另验证同标识改数量的 409 无副作用、另一个用户相同标识可独立创建、大小写 UUID 等价、缺失和非法标识被拒绝。

可复验脚本：

```bash
# 终端一：独立测试服务
PORT=4328 NODE_ENV=production ENABLE_DEMO_LIQUIDITY=false npm start
# 终端二
node scripts/verify-idempotency.mjs http://127.0.0.1:4328
```

原双账户交易脚本另在全新默认种子实例 4331 通过，覆盖价格撮合、部分成交、冻结、拒绝原子性、历史游标、身份隔离和生产静态入口：

```bash
node scripts/verify-trading.mjs http://127.0.0.1:4331
```

该脚本要求全新的默认种子服务；行情每秒变动时市场版本允许高于初始的 6，成交逻辑和精确现金断言不变。

### 服务已成交但响应丢失

使用独立生产服务 4330 和真实 Chrome。网络验收先把请求送给真实后端并取得响应，再丢弃返回浏览器的响应；没有伪造服务端成交。

1. 买入 SIM002 100 股，成交价 20.01，后端返回 201；浏览器收不到 POST 响应。
2. WebSocket 已更新可用资金到 997,999.00，页面仍保留待确认卡片并暂停新下单。
3. 刷新页面后，原委托恢复，没有新增 POST；切换到 SIM003，卡片仍显示原 SIM002 委托。
4. 点击重试，发送完全相同的业务参数与 UUID，返回 200、同一订单 ID、同一账户版本；不额外推送私有交易事件，确认后可以继续下单。

### POST 处理中刷新

1. 使用新的 UUID 买入 SIM003 100 股，成交价 30.01。等待真实后端提交完成，但暂不将响应交给页面。
2. 页面仍在等待 POST 时刷新，随后仅恢复待确认记录，没有自动提交。
3. 用户重试同一原请求，返回 200 和同一订单 ID。
4. 四次 HTTP 的状态为 201、200、201、200；最终恰好 2 张已成交订单、2 笔成交，可用现金 994,998.00。

浏览器验收无页面运行时错误。开发预览另在 5173 验证注册、实时代理、自动 UUID 与待确认卡片；该开发检查在浏览器侧截断 POST，没有创建测试挂单。桌面和 390px 手机宽度下的待确认卡片已截图并查看，无页面水平溢出；历史表格保留自身容器滚动。
