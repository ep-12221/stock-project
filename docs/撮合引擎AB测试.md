# 撮合引擎：价格树实现与 A/B 测试

## 实现与切换

默认撮合引擎改为 `price-tree`。每只股票的买卖两侧各维护一棵 AVL 树，树节点对应一个有挂单的价格；节点内是按服务端 `sequence` 排列的 FIFO 双向链表。订单 ID 映射到链表节点，最优买卖价分别缓存为买树最大键和卖树最小键。同价队列中不会再建一棵树。

| 部分           | 源码                                                                           | 职责                                            |
| -------------- | ------------------------------------------------------------------------------ | ----------------------------------------------- |
| 价格索引       | [avl-price-tree.ts](../apps/server/src/matching/avl-price-tree.ts)             | 查找、插入、删除、旋转、最小与最大价格缓存      |
| 新版订单簿     | [price-tree-book.ts](../apps/server/src/matching/price-tree-book.ts)           | 价档内 FIFO、只读撮合计划、价档更新的准备与提交 |
| 新版交易服务   | [trading.service.ts](../apps/server/src/services/trading.service.ts)           | 入参、幂等、撮合、冻结、结算与原子提交          |
| 原数组交易服务 | [trading-array.service.ts](../apps/server/src/legacy/trading-array.service.ts) | 完整保留原数组实现，作为对照组                  |
| 共享结算       | [settlement.ts](../apps/server/src/matching/settlement.ts)                     | 两版使用相同的冻结、成交结算、资产守恒检查      |

旧服务与基线提交 `ed483ca2b223f1ca66ed6a44aff4c12ab40ca262` 中的 `trading.service.ts` 逐字节相同，SHA-256 为 `1a6b5063eb66e07bb127b19005bd5a04e09a294d705169bb37df76c1d46db627`。原 `order-book.ts` 也保持不变。

在根目录 `.env` 中设置后重启后端：

```dotenv
MATCHING_ENGINE=price-tree
```

改为 `MATCHING_ENGINE=array` 可运行旧版。Docker Compose 读取同一个变量，重新创建容器后生效。内存账户、订单和成交会随重启清空；不支持带已有订单热切换。两版 HTTP、WebSocket 和前端协议一致。引擎选择属于整个 store 生命周期，A/B 在两个独立市场中回放相同指令，不把真实买卖委托随机分流到两个互不相通的盘口。

## 一次委托的处理

1. 按原规则校验用户、请求标识、参数、股票和委托数量限制；同标识重放直接返回原订单。
2. 读取对手侧最优价。不能成交时直接结束计划；可以成交时按价格优先遍历价档，再沿 FIFO 匹配。部分成交保留原节点和先后顺序，以 maker 的挂单价格成交。
3. 只读计划遇到自己的挂单时拒绝整个委托，之前计划中的外部成交也不提交。
4. 在受影响用户的账户、持仓和活跃订单索引副本上冻结、结算。准备需要删除的已成交节点和需要追加的剩余委托，预计算提交后的最优报价。
5. 所有业务校验、冻结核对、版本及资产守恒检查通过后，同步提交盘口和结算结果。提交阶段没有 `await` 或外部 I/O；旧计划或重复提交在修改盘口前被拒绝。WebSocket 通知仍在交易成功后发送。

这一提交边界针对现有单进程内存服务的业务拒绝与异常校验，不提供进程崩溃后的持久化恢复。启动系统挂单时也为草稿创建独立订单簿，后面的种子委托失败不会污染原树。

`buyOrderIds` / `sellOrderIds` 仅提供排序后的独立数组视图，供测试、诊断和启动检查使用。新版交易服务的撮合路径不生成这些数组。完整 AVL 高度、平衡度、队列和订单索引审计由测试执行；每次下单检查本次涉及的订单，继续完整核对受影响用户的冻结量。

## 复杂度与取舍

记订单簿有 `N` 笔活跃订单、单侧有 `L` 个有效价格档，本次匹配 `K` 笔订单，清空 `D` 个价档：

| 操作                         | 新版订单簿成本                             |
| ---------------------------- | ------------------------------------------ |
| 查看最优买卖价格、判断不交叉 | `O(1)`，读取缓存                           |
| 找到并追加到已有价档         | 找档 `O(log L)`，链表尾插 `O(1)`           |
| 创建新价档                   | `O(log L)`                                 |
| 生成撮合计划                 | `O(log L + K)`，不遍历不涉及的后续订单     |
| 移除成交订单、清空价档       | 链表更新 `O(K)`，价档删除合计 `O(D log L)` |
| 展开完整诊断视图             | `O(N + L)`，不在新版正常撮合路径中         |

树、价档和订单链表合计需要 `O(N + L)` 空间，并增加对象与指针管理成本。以上只描述订单簿；交易服务仍会复制受影响用户的数据、遍历其活跃委托核对冻结量、构造成交记录。因此整条下单链路不能标为 `O(log L)`，也没有实现对象池、无分配路径、跨进程排序或持久化日志。

旧版每次下单包含全盘口检查、数组映射、过滤、排序及替换。新版的性能收益同时来自价格索引和减少全盘口工作。两版业务校验及共享结算规则一致，但不再对不相关价档逐单审计；下面是两个实际实现的整体对照，不能当成只替换数组和 AVL 两种容器的实验。

## 正确性验证

- `npm run check`：695 项测试、34 个测试文件全部通过，同时通过类型检查、Lint、格式检查和生产构建。
- 价格优先、同价 FIFO、部分成交、跨价档成交、自成交拒绝、资金不足、整数与版本溢出、幂等及快照等原有核心业务套件，对 `array` 和 `price-tree` 分别执行。
- AVL 测试覆盖四种旋转、重复价格、随机插入删除与全部清空，每步检查高度和平衡；订单簿测试覆盖队列指针、部分成交保序、清空最优档、过期及重复提交无副作用。
- [逐笔对照测试](../apps/server/src/tests/matching-ab.test.ts)使用三组固定种子，各执行 400 条指令；每条比较返回值或错误、账户、持仓、委托、成交、盘口、索引、幂等记录和版本。仅把两次独立运行的随机订单及成交 UUID 归一为序号，忽略进程 epoch；拒绝时检查本版全部状态不变。
- 实际启动入口覆盖两种引擎及三种系统挂单配置，经过 HTTP 下单、WebSocket 首帧与账户推送、正常停机验证。
- 全量回归暴露并修复了一处原有实时测试的跨连接等待竞态：清空接收记录前等待所有连接收到上一轮消息，保留原来的精确帧数断言。

单独执行对照和树结构测试：

```bash
npm run test:matching:ab
```

## 性能测试方法

[benchmark-matching.mjs](../scripts/benchmark-matching.mjs) 调用编译后的生产 `submitOrder`，计时包含参数校验、幂等记录、撮合计划、冻结、结算及提交；不包含 HTTP、认证密码计算、WebSocket 或前端渲染。

- 每版每轮新建独立 Node 进程，串行执行；轮次顺序依次为 A/B、B/A、A/B。
- 每轮先在独立 store 预热 680 条命令，再创建测量 store 并建立初始盘口。预热、建簿和命令生成均不计时；开始测量前调用 GC，计时过程中保留自然 GC，不逐单强制 GC。
- 100 个买方和 100 个卖方轮流下单，初始现金及持仓相同。测试内两版使用相同的较大委托数量上限，以允许增长场景超过演示服务默认的 5,000 笔限制；正常服务上限不变。
- 三种场景 × 三档初始深度 × 三轮 × 两版，共 54 次测量；每次测量 2,040 条命令。每个请求都使用唯一的请求标识，幂等重放性能不在这组吞吐测量中。
- 每个 A/B 对照检查输入和最终交易状态的 SHA-256；检查发生在计时之后。每版额外检查现金、股数守恒，新版审计完整树和队列。
- 吞吐量按整段测量时间计算，包含计时循环本身的开销。延迟按单次同步命令调用计时，单位为微秒。汇总值为三轮各项指标的中位数，倍数为两个吞吐量中位数之比，P99 不是三轮样本池的合并分位数。

| 场景             | 指令流                                                                               | 初始与结束深度                                                    |
| ---------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| `resting-sparse` | 初始每个卖档一单；随后只挂不交叉的买单，最多占用 2,000 个买档                        | `N → N + 2,040`，不是恒定深度测试                                 |
| `fifo-dense`     | 初始全部卖单在同一价档；买入 1 股与补挂卖单交替，买卖各占 50%                        | 围绕 `N` 波动，结束为 `N`；共 1,020 笔成交                        |
| `sweep-sparse`   | 初始每个卖档一单；每 17 条命令中一笔买单吃掉 16 档，随后补 16 个更高卖档，补单也计时 | 在 `N-16` 到 `N` 间波动，结束为 `N`；120 笔主动买单、1,920 笔成交 |

执行与参数：

```bash
npm run bench:matching

# 指定另一份本地结果文件
npm run bench:matching -- --sizes=100,1000,4000 --samples=2040 --warmup=680 --rounds=3 --output=.deliverables/matching-ab-local.json
```

默认复测结果写入 `.deliverables/matching-ab.json`，包含环境、基线提交、实现源码 SHA-256、每轮指标、输入与交易状态摘要。下面这次完整测量的原始文件保留为 [benchmarks/matching-ab.json](benchmarks/matching-ab.json)，复测不会自动覆盖它。复测时应暂停其他重负载任务，并使用同一环境比较两版。

## 本次实测结果

测量时间：2026-09-07 00:58～01:01（UTC+8）。环境为 WSL2 Linux 5.15.153.1、AMD Ryzen 9 7940H、16 个逻辑 CPU、Node.js 22.14.0、V8 12.4.254.21。各进程串行执行，没有并行运行测试或构建来争用 CPU；未绑核，使用日常开发机器。

54 次测量共计 110,160 条计时命令，27 组 A/B 输入及最终交易状态摘要全部相同。下面的“初始挂单数”不是交易样本数，持续挂单场景会继续增长；吞吐量单位为命令/秒，P99 单位为微秒。

| 场景                  | 初始挂单数 | 数组吞吐量 | 价格树吞吐量 | 吞吐倍数 | 数组 P99 μs | 价格树 P99 μs |
| --------------------- | ---------: | ---------: | -----------: | -------: | ----------: | ------------: |
| 持续挂单，多价档      |        100 |      1,802 |       38,953 |    21.6× |     1,502.1 |          91.6 |
| 持续挂单，多价档      |      1,000 |      1,043 |       47,042 |    45.1× |     2,009.6 |          82.4 |
| 持续挂单，多价档      |      4,000 |        346 |       72,563 |   209.6× |     5,249.8 |          46.1 |
| 同价 FIFO，成交后补单 |        100 |     11,006 |       33,870 |     3.1× |       227.6 |         107.6 |
| 同价 FIFO，成交后补单 |      1,000 |      1,998 |       36,058 |    18.0× |     1,141.1 |          99.7 |
| 同价 FIFO，成交后补单 |      4,000 |        477 |       25,997 |    54.5× |     3,334.5 |         117.7 |
| 跨 16 档成交并补单    |        100 |     12,119 |       31,252 |     2.6× |       274.7 |         239.6 |
| 跨 16 档成交并补单    |      1,000 |      2,060 |       27,458 |    13.3× |     1,415.6 |         310.4 |
| 跨 16 档成交并补单    |      4,000 |        539 |       21,574 |    40.0× |     3,184.0 |         456.7 |

4,000 笔初始挂单时，持续挂单场景从 4,000 增长到 6,040 笔，全程没有成交；同价场景固定在一个价档，产生 1,020 笔成交；跨档场景结束时恢复为 4,000 个卖档，产生 1,920 笔成交。因此表中 72,563 命令/秒不能写成“每秒完成 72,563 笔成交”。

这次结果说明，避免整本盘口扫描和重建对当前实现有明显收益，深盘口尤为明显。在只有 100 笔初始挂单的跨档场景，吞吐收益约 2.6 倍，但 P99 只从 274.7 降至 239.6 微秒；需要结算的用户与成交数量同样影响延迟。

这是短时、三轮的本机微基准，没有测置信区间、饱和并发、长时间 GC 尾延迟或网络端到端耗时，也没有保证各轮 JIT 优化状态相同。不同初始深度的价格树吞吐量不完全单调，不能据此推断盘口越深越快。4,000 笔挂单时，价格树三轮内观测到的最大单次耗时仍达到约 1.1～2.5 毫秒，P99 不能代表最大延迟。

目前不能据此宣称达到高频交易平台的容量或延迟要求。后续若继续优化，应先分析账户副本与冻结校验、成交分配、历史数据增长，以及 HTTP / WebSocket 序列化，再用长时间、多种订单分布与固定负载测试确认收益。

## 生产入口复验

两种引擎分别启动编译后的 `apps/server/dist/index.js`，每次使用全新进程和独立端口：开启系统挂单时运行 `verify-trading.mjs`，关闭时运行 `verify-idempotency.mjs`，四组均通过。覆盖静态页面、真实成交、部分成交、失败无副作用、历史分页、会话隔离及 8 路同请求并发重放；测试进程均正常退出。Compose 配置解析也分别确认了 `array` / `price-tree` 环境变量传递正确。

## Demo 结构重构后的入口

后续重构将正式价格树流程合并到 `services/trading.service.ts`，旧服务逐字节移动到 `legacy/trading-array.service.ts`；`MATCHING_ENGINE` 配置和测试命令保持一致。前端下单与历史查询分别由 `trading.ts`、`history.ts` 管理，会话身份检查由 `auth.ts` 统一提供。

上文 54 次完整性能测量对应提交 `2f52495` 的重构前源码；原始 JSON 中的路径和 SHA-256 记录的是当时版本，不应拿已经移动的路径直接校验当前工作区。历史文件保持不变，新的复测结果按当前入口和源码摘要写到 `.deliverables/`。结构调整本身不作为新的性能提升结论。
