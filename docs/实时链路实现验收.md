# T06 实时链路实现与验收

日期：2026-09-06  
范围：服务端每秒行情、WebSocket 鉴权和状态推送、前端连接生命周期、实时历史合并及断线恢复。基础版本为 T05 的 371 个测试；本阶段新增 111 个测试，当前共 482 个（后端 278、前端 204），27 个测试文件。

## 1. 完成后的行为

- 服务端每秒统一更新三只股票的模拟最新价和涨跌幅，所有已登录浏览器看到同一市场状态。参考行情波动独立于撮合，不会产生订单或修改账户资金、持仓数量。
- 用户提交限价委托仍走 HTTP。提交后的本人快照与 WebSocket 共用版本校验；成交双方的有效会话都会收到自己的完整账户状态，无需点击刷新。
- 工作台实时展示委托状态、冻结量、持仓、现金、个人成交和匿名市场成交。市场视图不含用户身份、个人方向或订单 ID。
- 初次连接收到完整首帧前暂停下单。断线时保留资产和表单输入，显示数据可能过期；自动重连或手动重连拿到完整快照后恢复。
- 正常行情和成交更新不会触发定时 HTTP 轮询，也不会在每次自己下单后额外重查行情或历史。手动账户核对、首次历史查询及加载更多仍走 HTTP。

## 2. 服务端实现

### 行情与发布

`market.service.ts` 使用可注入随机数源，每秒每只股票抽取正负 1～20 个基点的变化，四舍五入到整数分，最小变化 1 分，价格限制在业务上下界。固定昨收价用来计算涨跌幅；达到价格边界时允许钳制后保持不变。

一批行情先完整计算，再更新存储并将 marketVersion 增加一次。非法随机数不会留下部分股票已更新的状态。每次市场快照包括所有股票和最近 50 笔匿名成交；随机行情不改变账户版本。

`realtime.service.ts` 复用 HTTP server 的 `/ws`，在 upgrade 阶段校验 Origin 白名单与 Cookie 会话。URL 不用于传递身份令牌；普通 HTTP `/ws` 返回 426 / UPGRADE_REQUIRED。WebSocket 是状态推送通道，客户端业务消息会被拒绝，下单只走 HTTP API。

认证、登记连接、构造首帧和把首帧加入发送队列在同一个同步步骤完成，中间没有 await。交易服务同步提交后，通过回调发布市场状态和受影响用户快照；同一交易即使多次成交，也只向每位受影响用户发布一次最终状态。发送失败不能回滚已提交的交易，也不能阻断其他连接。

### 事件与权限

| 事件 | 载荷 | 接收者 |
| --- | --- | --- |
| state.snapshot | market: MarketSnapshot；account: AccountStateDto | 新连接对应的用户 |
| market.updated | marketVersion、全部股票、最近 50 笔匿名成交 | 全部有效连接 |
| account.updated | userId、serverEpoch、accountVersion、账户、全部持仓、全部活跃单、最近 100 条关闭订单、最近 50 笔私人成交 | 受影响用户的全部有效会话连接 |

每个事件信封还包含 type、serverEpoch、emittedAt。私有数据始终按服务端会话用户生成；客户端同时检查事件与账户载荷中的服务实例、用户身份。

每次发送前重新验证会话。退出时通过撤销订阅立即关闭该会话的全部连接，到期计时器负责精确关闭过期会话，关闭码为 4401。其他用户以及同一用户未被撤销的独立会话不受影响。

### 连接资源

- 服务端每 30 秒 ping/pong 检查存活；浏览器协议栈负责响应 pong。
- 发送缓冲阈值为 1 MiB，包含本次待发送帧。超限或发送异常断开该连接，由恢复快照重新同步。
- 关闭 WebSocket 压缩，客户端向服务端发送的帧载荷上限为 1 KiB。
- 服务退出停止行情、心跳及会话清理定时器，停止接收 upgrade；以 1001 关闭连接，未回应关闭握手的连接最多等待 1 秒后终止。
- 生产入口直接创建实时服务；应用工厂仍能注入独立存储、会话和提交回调，便于隔离测试。

## 3. 前端一致性与恢复

App 在生命周期内启动一个 realtime store；登录身份、会话代次或服务实例改变时立即拆除旧连接及计时器，再建立新连接。离开应用时停止。各组件共享连接状态，不分别创建 WebSocket。

事件必须通过运行时结构校验。首帧先验证市场和账户两部分，全部合法后才能应用；首帧之前的增量事件不能解除同步状态。每个回调检查连接对象、本地连接代次及账户身份，旧连接消息或旧鉴权请求不能影响新会话。

账户和行情分别比较版本：旧 HTTP 响应不能覆盖新推送；合法但同版本或较旧的完整首帧可以完成握手，同时保留本地较新的数据。行情价格和匿名成交窗口分别记录已应用版本，避免 HTTP stocks 先返回较新报价后，把随后 WS 携带的有效成交窗口一起丢弃。

重连使用约 1、2、4、8、16、最多 30 秒指数退避，加入约 ±20% 抖动并限制最大等待；完整首帧后重置退避。连接到完整首帧最多等待 10 秒。同步后连续 15 秒没有合法更新也会触发断线处理，覆盖浏览器连接看似打开但实际不再收到数据的情形。

失败时可请求 `/api/auth/me` 确认身份，该请求最多等待 5 秒；仅明确 401 或已确认的身份 / 服务实例变化会清空登录，普通网络错误继续重试。身份探测不是正常行情轮询，也不延长会话有效期。

### 历史记录窗口

实时快照覆盖全部活跃订单、有限的近期关闭订单与成交。trading store 将窗口按记录 ID、版本和服务端序号合并到当前筛选，保留已加载的更早记录；旧 HTTP 活跃状态不能覆盖已成交状态。

当有限窗口不足以证明历史连续时，保留“加载更多”的补查游标。已清空分页缓存的初次查询或刷新期间，也比较前后完整活跃订单集合：旧活跃单消失且没有进入近期关闭窗口时，根据旧订单序号记录缺口。较早生成的 HTTP 空尾页不能把这个新缺口误判为历史已全部加载。

例如 sequence=100 的旧活跃单在请求期间成交，最近 100 条关闭记录仍为 sequence=600…501，延迟 HTTP 又返回 nextCursor=null。页面会保留 cursor=101 的补查入口，继续分页能取得该订单的最新成交状态。这一交错分别覆盖了首次加载和刷新场景。

结果不明的下单仍沿用 T05 保护：网络异常或 5xx 后保留输入、暂停重复提交，需要刷新账户并核对委托。实时更新或重连成功不能自行清除这种核对状态。T06 尚未提供幂等下单。

## 5. 真实 Chrome 验收

使用本次单独启动的生产构建服务（127.0.0.1:4327）及两个独立 Chrome 浏览器上下文，隔离 Cookie。没有用两个共享 Cookie 的普通标签假装不同用户。

### 无刷新成交

1. A 买入 SIM001 100 股，成交价 10.01；再以 11.01 挂卖 60 股。
2. B 以 11.01 买入 1,000 股，先匹配剩余 900 股系统卖单，再匹配 A 的 60 股，B 显示部分成交 960/1,000。
3. A 无刷新看到可用资金 999,659.60、卖单 60/60；再以 11.01 卖出剩余 40 股后清仓。
4. B 无刷新看到订单 1,000/1,000、可用资金 989,890.00、冻结现金为零。
5. 验收时移除账户刷新按钮，交易过程中行情与历史 HTTP GET 计数为 0。个人和匿名市场成交标签正确展示；输入的 12.34 不受每秒报价覆盖。

### 断线期间成交

1. 新账户 A 买入 SIM003 100 股，成交价 30.01，再以 31.01 挂卖 100 股。
2. A 浏览器切换离线，等待静默检测提示，确认下单不可用、旧资产与输入保留。
3. B 以 31.01 买入 1,000 股，吃掉 900 股系统剩余卖单及 A 的 100 股。A 离线期间继续显示旧快照。
4. A 恢复网络并点击重连；完整首帧后资金恢复为 1,000,100.00、持仓清空、委托 100/100，输入 31.01 保留。
5. 复制 B 会话 Cookie 创建另一个已连接页面；B 退出后两个页面均回到登录页，A 独立账户继续保持实时连接。

两轮浏览器验收均无页面运行时错误。生产构建结束后，另在现有 5173 开发预览完成注册、同源 WS 代理首帧、连续行情、输入保留及退出验收；无页面运行时错误。另检查 390px 手机宽度无页面横向溢出，历史表格在自身容器内滚动；桌面、手机及断线提示截图均已查看确认。
