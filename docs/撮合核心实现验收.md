# T03 撮合核心实现验收

## 1. 本阶段实现

- 同步限价委托服务，按股票独立维护买卖订单簿。
- 买盘价格从高到低、卖盘从低到高，同价按服务端接单序号排序；部分成交保留原序号。
- 以已有挂单价成交，支持跨多个价位、双方部分成交与剩余入簿。
- 买单先按完整限价金额冻结现金，卖单冻结股数；成交按实际金额结算。
- 价差通过减少冻结金额恢复可用余额，不额外增加总现金；买入股票可立即卖出。
- 对实际成交路径预演，遇到自己的订单整笔拒绝，先前预演的外部成交不提交。
- 受影响账户、持仓、订单和订单簿先在草稿计算，检查安全整数、冻结约束及资产守恒后同步提交。
- 每次成功命令，每个受影响用户账户版本仅增加一次，市场版本增加一次。
- 委托和成交全局序号、用户历史索引、活跃委托索引、市场成交索引。
- 每用户默认最多 100 条活跃委托，全市场默认 5,000 条；服务构造时可注入限制便于测试。
- 账户快照返回真实委托与成交：全部活跃委托、最近 100 条已结束委托、最近 50 笔个人成交，按序号倒序；公开 DTO 显式移除内部身份字段。
- 最优买卖报价随订单簿更新；模拟参考行情价不因撮合修改。

本阶段完成内部撮合能力。下单 HTTP 接口、历史分页、启动种子挂单属于 T04；交易页面属于 T05；定时行情和 WebSocket 属于 T06。幂等属于 T07，撤单属于 P2，均未提前提供入口。目前传入 clientOrderId 等未支持字段会被严格输入校验拒绝，不会静默忽略。

240 次混合委托的单个场景在每一步检查：

- 成功请求前后全市场现金总额、每只股票总股数不变，包括系统账户。
- 失败请求的所有内存 Map、数组、索引、报价、计数和版本与调用前一致。
- 冻结现金等于所有活跃买单的剩余限价金额；冻结股数等于对应股票的活跃卖单余量。
- 订单簿方向、股票、价格顺序、同价序号、唯一成员、终态移除及无交叉。
- 订单累计成交数量与金额等于对应成交记录之和。
- 买卖双方身份与订单一致，每笔使用 maker 价；双方交易记录索引一致。

## 4. 手算案例验收

先挂 B 卖单 100 股 × 1,000 分，再挂 C 卖单 50 股 × 980 分，A 买入限价为 1,020 分。

| A 委托数量 | 成交顺序 | 实际支出 | 剩余买单 | A 剩余冻结现金 |
| --- | --- | --- | --- | --- |
| 120 股 | C：50 × 980；B：70 × 1,000 | 119,000 分 | 0 股 | 0 分 |
| 200 股 | C：50 × 980；B：100 × 1,000 | 149,000 分 | 50 股 × 1,020 | 51,000 分 |

第一种情形先冻结 122,400 分，实际支出 119,000 分，3,400 分价差恢复可用；总现金仅减少实际成交金额。B 的剩余 30 股继续冻结。两种场景都通过精确整数断言。

## 5. 调用入口与实现组织

核心入口：

```ts
import { createTradingService } from './services/trading.service.js';

const trading = createTradingService(store);
const result = trading.submitLimitOrder(authenticatedUserId, {
  symbol: 'SIM001',
  side: 'BUY',
  priceCents: 1_020,
  quantity: 120,
});
```

调用是同步的，成功结果包含内部订单副本、成交副本、去重的 affectedUserIds 和 marketVersion。业务错误抛出 AppError，失败没有业务状态副作用。

| 文件 | 责任 |
| --- | --- |
| services/trading.service.ts | 严格输入校验、活跃上限、交易编排、序号、版本、索引与一次提交 |
| matching/order-book.ts | 买卖排序、活跃状态判断、只读成交预演及自成交拒绝 |
| matching/settlement.ts | 受影响用户草稿、资金/持仓冻结、逐笔结算、冻结与守恒检查 |
| matching/checked.ts | 非负安全整数与内部状态断言 |
| store/memory-store.ts、domain/models.ts | 订单、成交、订单簿及内存索引 |
| services/trading-dto.ts、services/account.service.ts | 脱敏 DTO 与真实账户快照 |

T04 接入时必须从已鉴权会话取用户 ID，不能使用请求体中的身份；内部系统账户可调用同一服务，但不可登录。SubmitOrderResult 包含内部双方身份，不应原样发送给客户端，应使用 DTO 和账户快照。核心提交结束后再安排响应与推送，外部发送失败不能回滚已成交状态。
